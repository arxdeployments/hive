# API contract — 3

ROUTER MOUNTING (main.py): conversations.router, messages.router, and groups.router ALL declare prefix="/api/conversations" and are included with no extra prefix, in registration order conversations (line 68) -> messages (69) -> groups (72); other routers (auth, admin, validation, contacts, dev, uploads, search, cross_org, org_admin, calls, ws) are mounted alongside. FastAPI resolves the overlapping literal/param segments without actual collisions in the current route set, but a rebuild must preserve the literal-vs-param distinctions ('direct', 'group', 'messages', 'members', 'leave', 'pin', 'read' as literals under the shared prefix). Note that message-level actions live at /api/conversations/messages/... (no conv_id segment) — react, forward, delete, info — while conversation-scoped message routes are /api/conversations/{conv_id}/messages[...].

AUTH (app/auth/middleware.py): require_auth validates a Bearer JWT with payload.type == "access" and returns the raw JWT payload; handlers read payload["user_id"], payload.get("org_id"), payload.get("name") (used verbatim as the actor display name in system messages and forward broadcasts — a stale token name produces stale system-message text). None of these three route files use require_org_admin/require_superadmin.

SERIALIZATION (app/utils/serializers.py): serialize_doc recursively converts ObjectId -> str and datetime -> ISO-8601 with trailing "Z" (naive datetimes assumed UTC); it copies whatever keys exist on the Mongo doc, so field presence varies by how the doc was created (system messages lack thumbnail_url/file_size/filename; direct-conv docs lack description/admin_only_messages). The Mongo doc id field is exposed as "_id" (string), NOT "id" — the frontend contract uses _id everywhere.

WEBSOCKET BROADCAST INVENTORY (app.websocket.manager: manager / ws_manager): broadcast_to_conversation(conv_id, payload, exclude_user=None) and send_to_user(user_id, payload). Event types emitted by these routes: reaction_update, new_message (forward-to-conversation only, with exclude_user=sender), message_deleted, conversation_created (group create to all members; also to newly added members), conversation_updated, member_added (to pre-existing members via send_to_user), member_removed, removed_from_conversation (direct to removed user), role_changed, member_left. CRITICAL GAP: POST /{conv_id}/messages (the main REST send) performs NO broadcast — real-time delivery depends entirely on the separate WS endpoint; likewise POST /direct (new direct conversation) and forward-to-contacts notify no one.

CROSS-CUTTING BUGS/PATTERNS a rebuild should fix (several corroborate the known-defects memory): (a) missing participant/org authorization on message-level actions (react, forward-source, delete-for-me, search has no org check) — cross-org data access is possible by ObjectId; (b) deleted_for and conversation participants.deleted_at are write-only (never filtered on read), so both per-user delete features are no-ops; (c) unescaped $regex in message search (injection/ReDoS); (d) N+1 query storms in every list/enrich path (users.find_one per participant/message, unread increments as one update per participant); (e) inconsistent enrichment shapes: group participants include joined_at, direct participants do not; reactions appear as raw [{user_id, emoji, created_at}] on Message but as [{user_id, user_name, emoji}] from the react endpoint; message-info returns {user_name}-only lists under the same read_by/delivered_to key names; last_message.sender_name fallback is "Unknown" in conversations.py but "System" in groups.py; (f) pagination defects in GET /api/conversations (post-limit search filtering, pinned_by array sort, Z-suffix cursor parse failing under fromisoformat on Python <3.11); (g) content sanitized only in send_message (sanitize_text) — group names/descriptions and filenames are not sanitized; (h) forwarding drops file_size/filename; (i) main.py's login rate-limit patch iterates auth.router.routes matching route.path == "/login", which will not match if the auth router declares a prefix (route paths include the prefix), meaning the 5/minute login limit is likely never applied — verify against auth.py in the rebuild; (j) all mutation flows are multi-step non-transactional Mongo writes (message insert + last_message_at set + per-participant unread increments) — a natural fit for a single Postgres transaction in the migration.

## GET /api/conversations
- file: /Users/adhityasathyakuamr/Documents/HIVE/RxHivexx-main/backend/app/routes/conversations.py
- auth: require_auth (JWT bearer access token; payload has user_id, org_id, role, name)
- request: Query params: cursor: Optional[str] (ISO datetime, compared as last_message_at < cursor), limit: int = 30 (ge=1, le=100), search: str = "", filter: str = "all" (accepts "all" | "unread" | "groups"). No body.
- response: {"data": [Conversation], "has_more": bool}. Conversation = serialized conv doc + enrichment: _id (str), type ("direct"|"group"), org_id (str), name (str|null), description (groups only), avatar_url (str|null), cross_org (bool), allowed_org_ids ([str]), created_by (str), created_at (ISO-8601 with Z), last_message_at (ISO Z), pinned_by ([str]), is_active (bool), admin_only_messages (groups only), participants: [{user_id (str), display_name, avatar_url, status (default "offline"), last_seen (ISO Z|null), unread_count (int), role (default "member")}], last_message: {content, sender_id, sender_name, created_at (ISO Z), type (default "text")} | null, unread_count (int, current user's), is_pinned (bool). If org_id missing from token: {"data": [], "has_more": false}.
- behavior: Lists conversations where user is a participant, is_active=true, and (org_id == user's org OR cross_org=true with user's org in allowed_org_ids). filter=unread adds $elemMatch on participants (user_id + unread_count>0); filter=groups adds type=group. Aggregation sorts by pinned_by:-1 then last_message_at:-1, limit+1 for has_more. Enriches each conv with a users.find_one per participant, latest non-deleted message, current user's unread_count, is_pinned. After fetching, applies `search` as a Python-side case-insensitive name match (other participant's display_name for direct, conv name for groups), then re-sorts: pinned first, unpinned by last_message.created_at desc. No side effects, no WS. BUGS: (1) server-side sort on the pinned_by ARRAY means other users' pins perturb everyone's ordering and break cursor pagination; (2) search filtering happens AFTER the limit, so pages can come back near-empty with has_more=true and matches silently skipped; (3) cursor parsed with datetime.fromisoformat inside try/except pass — the API emits datetimes with a 'Z' suffix which fromisoformat rejects on Python <3.11, so pagination silently returns page 1 forever; (4) DELETE /{conv_id} sets participants.$.deleted_at but this query never filters on it, so 'deleted' conversations still appear; (5) severe N+1 (one users query per participant per conversation + one messages query per conversation).
